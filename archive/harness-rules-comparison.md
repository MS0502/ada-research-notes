# 같은 과제를 네 가지 에이전트 실행 구성으로 비교하기

이 실험은 같은 시뮬레이션 최적화 과제에서 에이전트 실행 구성을 바꾸면 통과 수가 어떻게 달라지는지 봤습니다. 두 배치 모두 과제 식별자는 `edge2`, 실행 예산은 시행당 1,800초였습니다. 각 행의 분모는 해당 구성의 시행 수입니다.

| 실행 구성 | 첫 배치 m9 | 후속 배치 m10 |
| --- | ---: | ---: |
| 짧은 규칙 (`slim`) | 4/8 | 10/15 |
| 최소 구성 (`bare`) | 2/8 | 6/15 |
| 기존 구성 (`s80`) | 1/8 | 3/15 |
| 규칙이 많은 구성 (`heavy`) | 0/8 | 7/15 |

## 실제 소요 시간과 실행 환경

아래는 시행별 `agent_seconds`의 산술평균과 관측 범위입니다. 종료가 지연된 시행에서는 1,800초 예산보다 실제 경과 시간이 길었습니다. 첫 배치는 최대 5개, 후속 배치는 최대 8개 동시 실행으로 설정돼 있었습니다. [92회 시행 데이터](../data/harness/edge2-trials.csv)

| 실행 구성 | m9 평균 (최소–최대) 초 | m10 평균 (최소–최대) 초 |
| --- | ---: | ---: |
| `slim` | 1,752.54 (1,742.9–1,767.4) | 1,750.93 (1,743.1–1,779.2) |
| `bare` | 1,482.28 (371.9–1,823.0) | 1,776.81 (1,746.5–1,805.3) |
| `s80` | 1,559.76 (1,296.8–1,811.3) | 1,476.45 (1,015.2–1,806.2) |
| `heavy` | 1,750.89 (1,744.0–1,773.9) | 1,753.11 (1,743.3–1,820.2) |

각 실행은 `bare`, `slim`, `s80`, `heavy` 중 하나의 하네스 변형을 읽기 전용으로 마운트하고 같은 실험 프록시를 사용했습니다. 배치 명세와 결과표에는 시행별 가중치·양자화·엔진 빌드가 없습니다. 해당 중계 기록을 대조하기 전에는 모델의 정확한 버전 및 설정을 **미확인**으로 둡니다. 실행 결과는 원본 배치 로그에서 다시 집계했습니다.

현재 자료에서 확인할 수 있는 역할은 실험 실행기의 자동 실행과 판정, 외부 리뷰의 HTTP 로그 대조입니다. 네 변형 각각을 누가 처음 제안했는지는 보존된 두 배치 명세로 확인하지 못했습니다.

## 첫 표에서 놓치기 쉬웠던 점

첫 배치에서 `heavy` 조건의 세 시행에 HTTP 404가 한 번씩 기록됐고, 해당 요청은 재시도됐습니다. 위 표는 각 배치에 기록된 최종 통과 여부를 셌습니다. 404가 개별 판정에 얼마나 기여했는지는 여기서 분리해 측정하지 않았습니다.

`slim`은 두 배치에서 가장 많이 통과했습니다. `heavy`의 첫 배치 0/8은 후속에서 반복되지 않았습니다. 두 배치의 결과를 함께 보고해야 같은 조건의 결과가 얼마나 달라질 수 있는지 보입니다. 한 과제에서 관측한 순위이며, 다른 과제에서 규칙을 줄였을 때의 효과는 별도 실험이 필요합니다.

## 이후 비교에서 같이 기록할 항목

조건별 총 시행 수와 통과 수, 실행 예산, API 오류가 발생한 시행, 재시도와 최종 판정입니다. 별도 추론 속도 측정은 해당 측정의 모델·문맥·KV 조건과 함께 독립된 기록에 둡니다.
